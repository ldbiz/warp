# Caveats and unknowns

This file collects boundaries that cannot be fully confirmed from the client checkout. The rest of the pack avoids relying on these points.

## External systems not present here

- The implementations and deployment topology of Warp's application API, RTC GraphQL service, session-sharing service, Oz, remote workers, telemetry destinations, and release service are outside this repository.
- The GraphQL schema documents much of the client contract, but it does not establish server-side authorization, storage, retry, rollout, or consistency guarantees.
- Model-provider routing and availability can depend on server configuration, account entitlements, or credentials unavailable in the checkout.
- Internal channel configuration is generated by tooling not guaranteed to be installed in an OSS checkout. Exact Stable/Preview/Dev/Local URLs, keys, OAuth clients, update settings, and telemetry configuration therefore cannot be enumerated here.

## Runtime and platform context

- Native behavior varies across macOS, Windows, Linux/FreeBSD, and WebAssembly. A single-host inspection cannot confirm windowing, keychain, PTY, shell, updater, GPU, or packaging behavior on every target.
- `script/run` has platform-specific delegates and internal-versus-OSS behavior. The effective local binary can differ depending on whether internal channel tooling is available.
- Several optional Cargo features materially change the compiled app. There is no single binary that represents every valid feature combination.
- Remote proxy/daemon and browser/WASM paths are visible in the composition root, but their operational deployment and lifecycle are not fully described in public top-level documentation.

## Naming and architecture boundaries

- “AI Assistant,” “Agent Mode,” ambient/cloud agents, Oz, CLI agents, and orchestration overlap in user-visible purpose but represent distinct generations or execution contexts. Maintainers should clarify the preferred public terminology and which older surfaces remain strategic.
- `app/` contains both the desktop application and product models reused by the TUI. Directory location alone does not establish that a module is GUI-only.
- `warpui`, `warpui_core`, and `warpui_extras` divide renderer, core entity/element, and higher-level services, but the boundary is pragmatic rather than a strict layered architecture.
- Workspace/session terminology is used at both UI and cloud/API layers; types with similar names do not necessarily share lifecycle or persistence semantics.

## Tests and observable behavior

- Many cloud flows are covered with mocks, model tests, or stored fixtures rather than public end-to-end service tests. Production authentication, live synchronization conflicts, and provider failures require service-backed verification.
- GUI integration coverage is broad but subject to native/display timing; CI retries integration tests. That means a passing retry does not prove the absence of races.
- TUI render-to-lines tests validate deterministic cell output but not every terminal emulator's interpretation of escape sequences, color, clipboard, links, or image protocols.
- Persistence failures are intentionally degradable in startup. The precise user-facing behavior for every migration/corruption failure is not summarized by one central specification.
- Feature flags create behavior visible in code that may not be reachable in a given public channel or test cohort.

## Questions for maintainers

1. Which execution surface should contributors treat as canonical when shared Agent Mode behavior differs among desktop, `warp agent`, and `warp_tui`?
2. Which cloud-object conflict and offline semantics are stable public contracts versus implementation details?
3. What is the supported matrix for WebAssembly, remote daemon/proxy, and FreeBSD compared with the three primary desktop platforms?
4. Which generated channel/schema artifacts are expected to be available to external contributors, and which checks should gracefully skip without internal access?
5. Which integration scenarios are known flaky beyond the retries encoded in `.config/nextest.toml`?
6. What fixture refresh procedure preserves compatibility with historical SQLite migrations and released client versions?
7. Which legacy naming (`AI Assistant` versus Agent Mode, workspace versus session) should new documentation and code prefer?
